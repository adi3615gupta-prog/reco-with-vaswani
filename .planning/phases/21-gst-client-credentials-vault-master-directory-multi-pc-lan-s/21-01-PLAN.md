# Plan 21-01: Central Vault Storage Engine, Bidirectional Sync APIs & SQLite Schema Hardening

## Goal
Implement the central network credentials vault repository (`central_clients_vault.json`) and bidirectional synchronization service (`credentialsVaultSync.js`) with SQLite `clients` schema hardening. Ensure that adding, updating, bulk-importing, or deleting GST client portal credentials on any PC connected to the office LAN (`getActiveDataPath()`) automatically updates both local SQLite and the central network vault with timestamp-based conflict resolution.

---

## Tasks

- [x] **Task 1: Hardened SQLite Schema Migration & Indexing (`server.js`)**
  - In `server.js` startup table creation:
    - Add safe column migrations for `clients`:
      - `address TEXT`
      - `last_updated INTEGER DEFAULT 0`
      - `is_deleted INTEGER DEFAULT 0`
    - Create composite index on `clients(gstin, is_deleted)` for fast lookup and sync queries.
    - Pass `userDataPath` to `setupImsRoutes(app, db, userDataPath)` so IMS routes can resolve the shared data directory.

- [x] **Task 2: Central Vault Engine Service (`credentialsVaultSync.js`)**
  - Create `credentialsVaultSync.js`:
    - `getCentralVaultPath(dataPath)`: Resolves `<dataPath>/central_clients_vault.json`.
    - `readCentralVault(dataPath)`: Safely reads and parses `central_clients_vault.json` with JSON error recovery and default empty structure.
    - `writeCentralVault(dataPath, vaultData)`: Performs atomic write to prevent corruption across SMB network shares.
    - `syncCredentialsWithCentral(db, dataPath)`:
      - Reads all local rows from `clients` (active and soft-deleted).
      - Reads `central_clients_vault.json`.
      - Compares timestamps (`last_updated`):
        - Central newer than local -> Updates/inserts local SQLite record.
        - Local newer than central -> Updates/inserts central vault dictionary.
      - Handles soft deletions: if marked `is_deleted = 1` with newer timestamp, propagates deletion to both local and central without deleting row history.
      - Writes back to `central_clients_vault.json` if changes were pushed.
      - Returns summary: `{ success: true, pulledCount, pushedCount, totalClients, lastSyncTime }`.

- [x] **Task 3: Backend Routes Integration (`ims_routes.js` & `server.js`)**
  - In `ims_routes.js`:
    - Inject `getActiveDataPath` resolution using `defaultUserDataPath`.
    - In `GET /api/ims/credentials`:
      - Run `await syncCredentialsWithCentral(db, dataPath)` prior to returning records so any credentials updated on another PC are immediately fetched.
      - Filter out `is_deleted = 1`.
    - In `POST /api/ims/credentials/update`:
      - Set `last_updated = Date.now(), is_deleted = 0`.
      - Update local SQLite, then call `syncCredentialsWithCentral(db, dataPath)` to immediately push changes to the central network vault.
    - In `POST /api/ims/credentials/bulk-import`:
      - Set `last_updated = Date.now(), is_deleted = 0` for all imported clients.
      - Update local SQLite, then call `syncCredentialsWithCentral(db, dataPath)` to merge with central vault.
    - In `DELETE /api/ims/clients/:gstin`:
      - Soft-delete: `UPDATE clients SET is_deleted = 1, last_updated = ? WHERE gstin = ?`.
      - Push soft-delete to central vault so other PCs do not resurrect the client.
    - Add `POST /api/ims/credentials/sync-vault`:
      - Triggers manual or background synchronization and returns sync metrics.

- [x] **Task 4: Automated Verification Script**
  - Create a test script verifying:
    1. PC 1 saves credentials for client A -> central vault is created/updated.
    2. Simulated PC 2 (with blank SQLite) calls sync -> client A is pulled with portal username and password.
    3. PC 2 updates password with newer timestamp -> central vault reflects updated password.
    4. PC 1 calls sync -> PC 1 receives updated password without conflict.
    5. Soft deletion propagates correctly without resurrection.

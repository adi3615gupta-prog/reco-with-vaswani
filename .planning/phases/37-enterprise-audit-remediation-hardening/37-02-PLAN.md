<threat_model>
<threat>
  <id>T-37-04</id>
  <description>Plaintext taxpayer GST portal passwords and Gmail SMTP passwords readable over API, exported in Excel, and stored unencrypted on shared SMB network drives.</description>
  <mitigation>Encrypt at rest with AES-256-GCM (`cryptoVault.js`), never emit passwords in API JSON or template exports, and authenticate all credential/email routes.</mitigation>
</threat>
<threat>
  <id>T-37-05</id>
  <description>One-click mass purge of 400+ clients via `mirrorMode: true` and `deleteMissing = true` default on bulk import without confirmation or admin role check.</description>
  <mitigation>Default both frontend `mirrorMode` and backend `deleteMissing` to `false`, require `req.user.role === 'admin'`, and show count confirmation modal.</mitigation>
</threat>
<threat>
  <id>T-37-06</id>
  <description>One-way-door lockout risk when deploying strict `firestore.rules` or rotating Firebase/GCP keys while older unauthenticated desktop clients or legacy plaintext `network_users` exist.</description>
  <mitigation>Auto-hash legacy plaintext user passwords on server startup before disabling plaintext login fallback, and gate live Firestore rules deployment + GCP key revocation behind an explicit `checkpoint:decision` after migrating server/client queries.</mitigation>
</threat>
</threat_model>

<task id="37-02-T1">
  <name>Create AES-256-GCM Vault Encryption Utility & Upgrade Sync/Storage (`cryptoVault.js`, `credentialsVaultSync.js`)</name>
  <description>
    1. Create `cryptoVault.js` using Node built-in `crypto`:
       - Key management: read `process.env.VAULT_MASTER_KEY`, or load/generate a 32-byte random key stored in local `USER_DATA_PATH/.vault_key` (with restricted file permissions; NEVER stored inside `gst_returns_data` SMB share), with optional deterministic office-key derivation from `office_id + process.env.OFFICE_VAULT_SECRET` when multiple LAN server nodes share `central_clients_vault.json`.
       - `encryptSecret(plaintext)`: returns `''` for empty; if already `enc:v1:...`, returns as-is; otherwise encrypts via `aes-256-gcm` with random 12-byte IV and auth tag, formatted as `enc:v1:<iv_b64>:<tag_b64>:<ct_b64>`.
       - `decryptSecret(value)`: returns `''` for empty; if NOT prefixed with `enc:v1:`, returns raw value (transparent legacy plaintext support during migration); otherwise authenticates and decrypts GCM payload.
       - `isEncryptedSecret(value)`: boolean check for `enc:v1:` prefix.
    2. Update `credentialsVaultSync.js`:
       - Encrypt `portal_password` via `encryptSecret()` before writing to `central_clients_vault.json` or inserting/updating SQLite.
       - On `syncCredentialsWithCentral()`, detect any legacy plaintext passwords in SQLite or central vault and transparently upgrade them to `enc:v1:...` format.
    3. Update `server.js` startup migration:
       - Re-hash any legacy plaintext passwords in `network_users` (`!password.startsWith('$2')`) with `bcrypt.hash(password, 10)` on startup, then remove the plaintext password fallback (`if (user.password && !user.password.startsWith('$2'))`) from `POST /api/login`.
       - Re-encrypt any legacy plaintext `clients.portal_password` and `ims_email_settings.app_password` rows at startup.
  </description>
